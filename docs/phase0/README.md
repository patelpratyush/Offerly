## Selected architecture and budget

- Keep React/TypeScript/Vite frontend and Express on Node.js 24. Existing production runs on Vercel with Supabase PostgreSQL in a private schema, verified TLS, server-side ownership checks, and a dedicated runtime role. SQLite remains the isolated local development/test option.
- Keep private Vercel Blob documents and isolated ClamAV Sandbox scans. Existing Supabase Cron schedules reviews, reminders, file cleanup, and scanner maintenance. These are existing services; this phase adds no public job catalog, mailbox data store, or production model endpoint.
- Owner chose **$0 additional AI spend for Phase 0**. Do not buy credits, enable auto top-up, install paid providers, or change plan subscriptions. Existing hosting/database/storage/scan charges are outside this additional-AI budget and are not promised to be zero. Monitor provider dashboards before enlarging the pilot.
- Vercel AI Gateway OIDC authenticated after refreshing local credentials, but `/v1/credits` reported zero balance. An attempted zero-priced synthetic request returned `customer_verification_required` before generation. No successful paid or cloud inference occurred. Gateway is a possible future hosted route, not a validated production model dependency.
- Local Ollama was already installed. The original baseline used `qwen3:0.6b`; stronger `qwen3:4b` was evaluated on an 8 GiB Mac. Full results, model digest, prompt and fixture hashes, timings and failures are retained. Neither model meets launch quality, runs in production, or may mutate application stages. A paid GPT API could be evaluated on synthetic data if existing free credits are verified; no API request or model addition is authorized under the $0 additional-spend limit. Any real-mail processing requires explicit external-processing consent first.
- Initial pilot remains two invited users, no billing feature, no automatic status changes, no outgoing messages, and no automated applications. Before a larger pilot, declare message/listing volumes, choose a hosted inference budget, and measure actual cost per active user.

## Mailbox and model data boundaries

Production sync target: check connected Gmail accounts every two hours using the Gmail History API and a per-account `historyId`, rather than repeatedly scanning seven days. Perform an initial bounded sync to establish the cursor; if Google returns 404 for an expired cursor, do a deduplicated full resync. The existing Supabase cron can dispatch due sync work. The current Hobby Vercel Cron restriction is once daily, so do not schedule a two-hour Vercel Cron without a plan that supports it. New mail should create evidence-backed review items; user approves application changes. This production integration is not implemented. See [Gmail synchronization](https://developers.google.com/workspace/gmail/api/guides/sync), [history.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list), and [Vercel Cron limits](https://vercel.com/docs/cron-jobs/manage-cron-jobs).

The owner explicitly authorized reading all emails, including personal messages, across mailbox history on October 22, 2026. The local proof may paginate the full mailbox, including Spam and Trash, but must process one message at a time without fetching separate attachments or decoding/saving inline attachment parts (which Gmail may include in MIME responses). A Google browser authorization is still required. Owner requested reusable access: keep refresh credentials in macOS Keychain and access tokens/message content in memory. Do not persist unrelated mail, export bodies, or send personal mailbox content to model providers. Retain only aggregate counts without message identifiers, addresses, subjects, or bodies. Retain the reusable Keychain grant until explicit disconnect or Google expiry/revocation; clear in-memory token references at exit.

The model evaluation uses only checked-in fictional cases. Inputs exclude gold labels and rationale. Freeze inputs and prompt before held-out execution. Keep independent predictions and failures; do not repair outputs using labels or tune a second prompt against held-out answers. Small synthetic scores never open the PRD automatic-update gate. Review-only behavior stays mandatory.

Future durable Gmail access requires encrypted credential storage, disconnect/revocation semantics, retention decisions, minimized evidence, and applicable Google review. Domain-free Desktop testing does not solve hosted/public OAuth readiness. See [Gmail setup and acceptance](gmail.md).

## Commands

```sh
npm run phase0:sources
npm run phase0:gmail
# After explicit consent; opens Google browser authorization:
npm run phase0:gmail:live -- --last-7-days
npm run phase0:import
npm run phase0:test
```

`phase0:sources` reads the fixed public sample boards and writes metadata-only technical evidence. `phase0:gmail` inspects private local configuration without network/mailbox access and exits 2 when unavailable. `phase0:import` uses saved Keychain authorization to select at most 20 recent recruiting messages, produce memory-only review candidates, and check duplicate-free replay. `phase0:model` performs local synthetic inference only, with fixed model/split/prompt options and exclusive artifact writes; recorded runs refuse overwrite or implicit re-evaluation. It never connects Gmail or mutates an application. Commands are validation tools, not shipped discovery/import UI.

## Phase boundaries and remaining gate

Bounded Phase 0 feasibility work is recorded, including model failure and release recommendation. Formal Phase 0 exit is **not passed**: current prototype does **not** meet the PRD quality gate for production extraction/matching. Next model decision: run a synthetic-only GPT API comparison only after confirming usable free credits and a server-side secret; otherwise keep AI matching deferred. Any winning candidate still needs representative, independently human-labeled consented data before release. No synthetic score enables automatic updates.

Hosted web OAuth, per-user encrypted credentials, resumable two-hour History API sync, importing applications into the actual workspace, and complete recruiting-event/contact extraction belong to Phase 2. Public source permissions and discovery collection belong to Phase 3. Full-history scanning is not required to prove this explicitly bounded Phase 0 import. The [access decision](access-decision.md) records these boundaries.

No new delivery date is estimated from this spike. M2 planning depends on model quality and privacy choice, Google hosted OAuth approval, credential lifecycle/storage, durable incremental sync, review-queue wiring, and representative human-reviewed acceptance data. Re-estimate after model/API budget access and hosted OAuth feasibility are resolved; the integration prototype does not validate the broader delivery timeline.
