# Security status and operating requirements

No application can be certified to have zero security risk. This repository has a tested security-hardening baseline; it is **not approved for unrestricted public deployment**. Dependency audits and automated tests are evidence about specific controls, not guarantees against unknown vulnerabilities.

## Implemented protections

- Account-scoped database reads, private file downloads, document-version links, timelines, duplicate reviews, import previews, and exports. Regression tests exercise cross-account denials.
- Password hashing uses asynchronous scrypt with N=131072, r=8, p=1 and a random per-password salt. At most two hashes run concurrently. Existing lower-cost hashes migrate after successful login. New passwords require 15–256 characters; login accepts existing shorter passwords. No composition rules or silent truncation.
- Browser account state is remounted on logout, detected session expiry and account changes. Late responses from an earlier session are discarded; timeline responses are scoped to the currently open application. Supporting browsers propagate session resets between tabs through BroadcastChannel without sharing credentials.
- Session IDs are random 256-bit values; only SHA-256 digests are stored. Sessions expire after 12 hours or 30 minutes of inactivity. Production cookies use the `__Host-` prefix, Secure, HttpOnly, SameSite=Strict and Path=/ without Domain. Login rotates the presented session; password changes revoke every session and recheck the initiating session after asynchronous hashing, before committing. Deletion requires the current password and confirmation email.
- Production startup requires an exact HTTPS APP_ORIGIN. Host and HTTPS checks, same-origin mutation checks, Fetch Metadata checks, JSON-only mutation requests, and a required custom request header protect against browser cross-site requests. No cross-origin credentialed API is enabled. Non-browser clients may omit Origin but must supply the custom header.
- SQLite-backed bounded rate-limit buckets survive app restarts. IP and account limits constrain authentication; authenticated mutation, import, upload, and export limits constrain resource abuse. Proxy headers are ignored unless a loopback proxy is explicitly trusted.
- Separate body limits: 256 KB normal requests, 3 MB imports, 28 MB upload JSON. Large bodies are parsed only after authentication. Compressed bodies are rejected. Password work, uploads and exports have concurrency limits. Server header/body timeouts bound slow requests.
- PDF header/trailer checks and DOCX ZIP structure, required package entries, expansion, encryption, embedded-object, macro-name and entity checks. These are validation checks, **not sanitization or proof of a harmless document**. Production uploads require a functioning ClamAV INSTREAM scanner and fail closed on errors/timeouts. Legacy unscanned files are blocked from downloads and omitted from production exports until re-uploaded. Files are downloaded as attachments with a sandbox CSP.
- Per-account file limit: 100 MB / 100 files, 20 MB per file. Records/history/import previews have separate limits. Exports write files individually instead of constructing one giant file array. Duplicate suggestion generation is bounded and reports partial scans.
- API responses are no-store; CSP disallows executable inline scripts, objects, external scripts and framing. User text is rendered through React escaping; URLs accept HTTP(S) only. CSV exports escape formula-leading values.
- SQL uses bound values. Unknown record kinds, malformed inputs, and unowned relations are rejected. Unexpected errors return a generic message and request ID; logs omit request bodies, credentials, emails and database messages.
- SQLite files/WAL/SHM use restrictive permissions; new process files use umask 077. SQLite secure_delete is enabled. This does not erase existing backups, historical WAL pages, snapshots, or SSD remnants.
- Pinned CI action revisions, a lockfile, lint, regression tests, build/type checking, dependency audit and scheduled dependency PR configuration are included. CI must actually be enabled and branch protection configured in the hosting platform.

Contact provenance and confirmations are user-recorded assertions, not external identity verification. Changing contact values clears inherited confirmation and stale evidence. Submitted-document evidence is derived from owned immutable files; later uploads cannot replace recorded bytes. Listing revisions are server-recorded and cannot be edited through the record API; recording time is distinct from user-supplied capture date. Application and listing-history writes share one transaction, including quota failures. Full account deletion removes these records and their histories.

Recruiting evidence is explicitly supplied by the user and never treated as executable instructions. The worker performs no network requests or AI extraction. Reviews require an authenticated decision; version checks, field locks, chronology checks and transactional receipts protect updates and undo. Evidence timestamps and excerpts remain user assertions, not externally verified facts. Reminders are date-only in-app records with no outbound sending. A separate worker shares the private SQLite database; supervise the API service and its child process together.

## Deployment requirements

1. Use Node 24 and install from the committed lockfile (`npm ci --ignore-scripts`). Build with `npm run build`. Run as a dedicated unprivileged OS user, not root. Do not use the Vite development server publicly.
2. Set APP_ORIGIN, DATABASE_PATH and proxy settings in your process manager. `.env.example` is documentation, not an automatically loaded secret file. Never commit real invitation codes or scanner credentials.
3. Terminate TLS with valid certificates. `deploy/nginx.conf.example` illustrates a same-host proxy that overwrites forwarding headers. Restrict direct access to Node; it binds to 127.0.0.1. Keep proxy and OS patched. Add deployment-level request/connection/storage quotas.
4. New registrations are disabled in production unless REGISTRATION_TOKEN is configured (at least 32 random characters). Share/rotate it through a secure channel. The current authentication model is for an invited pilot. Email verification, self-service password recovery, MFA/passkeys and abuse-resistant public signup are still required before a public account service.
5. Configure a locally accessible ClamAV daemon socket via CLAMAV_SOCKET, keep signatures current, and set its StreamMaxLength to at least 20 MB. Test EICAR rejection and scanner-outage behavior in the actual deployment. Tests here use a protocol fixture, **not a live antivirus daemon**. Uploads stay unavailable without a scanner; manual tracking remains usable.
6. Put the database on a private encrypted persistent volume with sufficient capacity. Encryption and key management are deployment responsibilities; this SQLite database is not application-level encrypted. Use one app instance per SQLite database on a local filesystem. This is not a multi-region or horizontally scaled architecture.
7. Back up SQLite using an online backup facility or a consistent stopped-instance snapshot, not a blind copy of an active WAL-mode file. Encrypt backups, restrict restore access, and test restoration and retention/deletion schedules. Local backup/restore tooling is provided (see `docs/BACKUP_RESTORE.md`); scheduling, encryption, off-host storage and deployment restoration drills are not configured here.
8. Configure monitoring/alerts for repeated errors, throttling, scanner failures, disk pressure, certificate expiry and backup failures. The current redacted logs are a starting point, not an incident-response platform.
9. Complete an independent security review, deployment penetration test, accessibility review and declared-load test before launch. No 100-user availability/performance target has been demonstrated.

## Operational limits and lifecycle

Rate buckets contain only hashed identifiers and counters, and expired buckets are pruned on requests. Uncommitted previews expire after one hour. Successful import batches keep a compact replay receipt for seven days; original row payloads are removed at commit. Workspace history is limited to 50,000 events / 32 MB and 10,000 records per account; cap exhaustion returns an explicit error. Duplicate review returns at most 100 suggestions with a bounded comparison count.

Bulk edits validate all selected owners and versions in one transaction and retain bounded replay receipts for seven days (up to 1,000 per account; expired receipts are pruned on bulk requests). Duplicate merges require a preview fingerprint, support up to 100 linked records with a bounded undo snapshot, and refuse reversal after any affected record changes. Saved views are private account records.

All private exports require authentication. An unscanned file omitted from a production export is listed with an explicit reason. Logout and password changes revoke sessions, but cannot retract data already downloaded. Account deletion removes live owned rows and session credentials; backup retention and physical erasure require the deployment procedures above.

## Verification

Run `npm run check` and `npm run test:e2e`. Browser tests start an isolated temporary database and dedicated loopback ports 4173/3002; they refuse to reuse an existing server, preserve normal rate limits, and remove the temporary database after normal shutdown. Lint covers backend JavaScript, tests and runtime configuration; frontend verification uses strict TypeScript and browser tests. Security tests include forged request origins/hosts, missing headers, session idle/absolute expiry, revocation, deletion/password reauthentication, cross-user data/file access, scanner protocol responses, upload rejection, response error redaction and legacy password upgrades. Tested behavior is limited to the scenarios in the test suite.

Guidance used: [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

Report suspected vulnerabilities privately to the repository owner. Do not post live credentials or private application data in public issues. A dedicated disclosure contact and response SLA must be established before public launch.
